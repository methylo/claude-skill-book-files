# 책 원고 퇴고 워크플로우 (Book Editing Workflow) v1.1

완성된 챕터(또는 전체 원고)를 입력받아, 3회 패스 편집을 실행하고, 편집된 원고와 체크리스트 리포트를 산출하는 스킬이다.

## 파이프라인 규약

책 프로젝트 폴더에 `00 파이프라인 규약.md`가 있으면, 파일명·문체 정본·역할 경계에서 이 스킬의 기본값보다 규약 파일을 먼저 따른다. 규약 파일은 선택 사항이다. 없으면 이 문서의 기본값으로 진행한다.

## 스킬 체인 내 위치

```
[층 0] book-planning
[층 1] book-research → book-writing-pro → [book-editing] ← 이 스킬   (챕터마다 반복)
[층 2] book-feedback-reader (게이트)
[층 3] book-citation → book-writing-pro Phase 7
```

챕터 루프의 마지막 단계다. 집필(book-writing-pro Phase 3~4) 완료 후, 피드백 게이트와 출처 표기 이전에 실행한다.

**이 스킬이 3회 패스 퇴고의 정본이다.** book-writing-pro Phase 6은 자체 절차를 정의하지 않고 이 스킬을 호출한다. 독립 스킬이므로 이미 완성된 원고에 대해 언제든 단독 실행할 수 있다.

## 입력 요건

퇴고를 시작하기 전에 다음을 확인한다:

1. **원고 파일**: 챕터 단위(.md) 또는 통합 원고(.md, .docx)
2. **문체 정본** (선택): 아래 "문체 가이드 적용 우선순위"대로 찾는다. 하나도 없으면 원고의 기존 문체를 기준으로 삼는다
3. **종결어미 지정** (선택): `~다`체 / `~합니다`체. `00 기획 인계.md` 슬롯 0에 값이 있으면 그것을 쓴다. 없으면 원고의 기존 종결어미를 유지
5. **참조 자료 팩** (선택): 프로젝트 폴더에 해당 챕터의 `research-Ch[번호].md`가 있으면 자동 탐색한다. **B 모드 팩(제목에 "(확장)")이 있으면 퇴고 근거로 우선 사용한다** (아래 "자료 팩 반영 퇴고" 참조)

사용자가 "퇴고해줘"만 말해도 실행 가능하다. 원고 파일만 있으면 된다.

## 3회 패스 편집 프로세스

퇴고는 한 번에 모든 것을 고치려 하지 않는다. 각 패스는 서로 다른 층위를 점검하며, 이전 패스의 결과 위에서 다음 패스가 작동한다. 전문 편집자가 원고를 3번 읽는 이유와 같다 — 한 번에 구조와 맞춤법을 동시에 보면 둘 다 놓친다.

### Pass 1: 구조 편집 (Structural Edit)

전체 흐름과 챕터 단위 논리를 점검한다. 문장 수준은 건드리지 않는다.

**점검 항목 (14개):**

| # | 항목 | 판단 기준 |
|---|------|----------|
| 1 | 전체 논지 아크 | 처음부터 끝까지 논리적으로 흐르는가 |
| 2 | 챕터 목적 | 각 챕터가 전체 흐름을 전진시키는가 |
| 3 | 페이싱 균형 | 늘어지거나 급한 챕터 없는가 |
| 4 | 도입부 훅 | 첫 문단이 "왜 이 주제인가"를 설득하는가 |
| 5 | 결말 일관성 | 결말이 전제와 일관되고 만족스러운가 |
| 6 | 챕터 첫 문장 | "왜 필요한가"를 설명하는가 |
| 7 | 설명 순서 | 개념 → 판단 기준 → 적용 방식을 따르는가 |
| 8 | 소제목 설계 | 행동·판단 중심 문장인가 (기능명 나열 아닌가) |
| 9 | 실무 정리 블록 | 챕터 말미에 정리 블록이 있는가 |
| 10 | 중복·모순 | 중복되거나 모순되는 내용이 없는가 (B 모드 팩의 ⑥ 교차 인용이 있으면 대조 근거로 사용) |
| 11 | 이탈 징후 A | 방법이 기준보다 앞서는 장은 없는가 |
| 12 | 이탈 징후 B | 감정적 동기부여가 논리를 앞서는 장은 없는가 |
| 13 | 이탈 징후 C | 읽고 나서 기준 변화 없이 "뭘 하면 되지?"만 남는 장은 없는가 |
| 14 | 경험·사례 논증 | 사례가 판단 기준과 무관하게 나열만 된 곳은 없는가 |

**Pass 1 실행 방법:**
1. 원고 전체(또는 대상 챕터)를 읽고, 14개 항목을 하나씩 점검한다
2. 문제가 발견된 항목은 해당 위치와 수정 방향을 기록한다
3. 구조 수정이 필요한 부분을 먼저 고친다 (문단 이동, 소제목 변경, 도입부 재작성 등)
4. Pass 1 결과를 리포트에 기록한 후 Pass 2로 진입한다

### Pass 2: 문장 편집 (Line Edit)

문장 단위의 문체, 리듬, 톤을 점검한다.

**점검 항목 (11개):**

| # | 항목 | 판단 기준 |
|---|------|----------|
| 1 | 문장 명확성 | 40~70자 기준으로 간결한가 |
| 2 | 문체·톤 일관성 | 전체적으로 일관되는가 |
| 3 | 종결어미 통일 | `~다`/`~합니다` 혼용 없는가 |
| 4 | 문단 전환 | 전환이 자연스러운가 |
| 5 | 단정적 서술 | "가능하다" 대신 "이렇게 판단한다" 사용하는가 |
| 6 | 용어 설명 | 전문 용어가 한글(영문) 병기 되어 있는가 |
| 7 | 감정·감탄 표현 | 감정적/감탄형/과장 표현이 없는가 |
| 8 | 문장 리듬 | 단문/중문 교차 배치가 되어 있는가 |
| 9 | 줄바꿈 | 문단 단위로만 적용되는가 |
| 10 | 볼드 강조 | 핵심 기준·판단 포인트에 볼드가 적용되어 있는가 |
| 11 | 경험 문단 톤 | 경험 유형(직접경험/관찰/실패담 등)에 맞는 서술 톤인가 |

**금지어 점검 (Pass 2에서 함께 실행):**

| # | 점검 | 대응 |
|---|------|------|
| 1 | "~할 수 있습니다" 유무 | 단정형으로 전환 |
| 2 | "매우, 쉽게, 빠르게" 유무 | 수치·조건으로 대체 |
| 3 | 근거 없는 형용사 유무 | 비교 기준 추가 또는 삭제 |
| 4 | 추상 명사 중심 문장 유무 | 동사 중심 문장으로 전환 |
| 5 | 판단이 드러나는가 | 판단문 추가 |
| 6 | 실행 기준이 있는가 | 기준 명시 |

**AI 흔적 제거 (Pass 2 핵심 작업):**

다음 패턴을 탐지하고 제거한다:
- 과장형 형용사: 혁신적인, 획기적인, 창의적인, 강력한, 완벽한, 최고의, 탁월한, 뛰어난
- 모호한 부사: 매우, 굉장히, 상당히, 꽤, 쉽게, 빠르게, 간편하게, 효율적으로
- 추측·완곡: ~할 수 있습니다, ~일 수 있습니다, ~라고 볼 수 있습니다, 어느 정도, 다소
- 여유 연결어: 전반적으로 볼 때, 일반적으로 말하면, 결과적으로, 따라서
- AI 문장 구조: ~라고 할 수 있습니다, 비로소 ~됩니다, 뿐만 아니라, 끊임없는, 한층 더
- 부사+형용사+가능성+추상명사 조합

**Pass 2 실행 방법:**
1. Pass 1에서 구조가 잡힌 원고를 문장 단위로 읽는다
2. 11개 항목 + 금지어 6개 + AI 흔적 패턴을 동시에 점검한다
3. 문제 문장을 수정한다. 수정 시 원본 의미를 보존하되, 문체와 리듬을 정비한다
4. 종결어미 통일 여부를 전수 검사한다
5. Pass 2 결과를 리포트에 기록한 후 Pass 3로 진입한다

### Pass 3: 교정 (Proofreading)

최종 표면 오류를 잡는다. 내용은 건드리지 않는다.

**점검 항목 (9개):**

| # | 항목 |
|---|------|
| 1 | 맞춤법·띄어쓰기 오류 수정 |
| 2 | 문법·구두점 검증 |
| 3 | 서식 일관성 (제목, 마크다운, 간격) |
| 4 | 이름, 날짜, 사실관계 일관성 |
| 5 | 목차와 본문 제목 일치 |
| 6 | 모든 `[TODO]` 마커 해결 또는 제거 |
| 7 | 인용·참조 서식 통일 — 원고 내 표기의 형식 통일만 담당한다. **정식 출처 표기·참고문헌 생성은 book-citation 담당**이므로 여기서 새 출처를 만들지 않는다 |
| 8 | 금지 표현 최종 점검 (기능 나열, 감상형, AI 대체 표현) |
| 9 | 최종 글자 수 기록 |

## 편집 후 재검증 (Evaluator 패스)

3회 패스 완료 후, 편집 결과물 자체를 완성 조건으로 재검증한다. 편집한 시점과 검증하는 시점을 분리해, 수정 과정에서 새로 생긴 문제를 잡는 것이 목적이다.

**재검증 항목:**
- [ ] 금지어·AI 흔적 0건 (Pass 2에서 수정한 문장 포함 전수 재확인)
- [ ] 종결어미 통일 (수정 문장에서 혼용이 새로 생기지 않았는가)
- [ ] 분량이 모드별 제한 범위 안인가
- [ ] 원본의 사실·수치·고유명사가 편집 과정에서 변형되지 않았는가
- [ ] B 모드 팩 사용 시: "검증 결과: 불일치" 항목이 모두 수정되었는가

**재점검 루프:** 미달 항목이 있으면 해당 항목만 수정 후 재검증한다 (최대 2회). 2회 후에도 미달이면 미달 항목·위치·사유를 사용자에게 보고한다. 재검증 결과는 편집 리포트에 1줄로 기록한다.

## 퇴고 모드

사용자의 요청 범위에 따라 3가지 모드로 실행한다:

### Light 모드
- **트리거**: "다듬어줘", "문장 정리해줘", "가볍게 퇴고"
- **범위**: Pass 2 + Pass 3만 실행
- **원칙**: 원본의 문장 수·문단 수·전체 구조를 유지한 채 표현만 정리한다. 새로운 문장이나 문단을 추가하지 않는다
- **분량 제한**: 원본 대비 100~105%

### Standard 모드
- **트리거**: "퇴고해줘", "교정해줘", "원고 점검해줘"
- **범위**: Pass 1 + Pass 2 + Pass 3 전체 실행
- **원칙**: 구조 조정 허용. 문단 이동, 소제목 변경, 도입부 재작성 가능
- **분량 제한**: 원본 대비 95~110%

### Deep 모드
- **트리거**: "전면 퇴고", "깊은 퇴고", "리라이팅 수준으로"
- **범위**: Pass 1 + Pass 2 + Pass 3 + 추가 점검
- **추가 점검**: 근거 보강 필요 구간 식별, 사례 교체·추가 제안, 반론·균형 점검
- **원칙**: 문단 단위 재작성 허용. 구조 재설계 가능
- **분량 제한**: 원본 대비 90~120%

모드를 명시하지 않으면 Standard 모드로 실행한다.

## 자료 팩 반영 퇴고

리서치 스킬(book-research)로 생성한 참조 자료 팩(.md)이 있는 경우, 퇴고 시 함께 반영한다. 이 경우 Deep 모드를 적용한다.

### B 모드 팩 우선 규칙 (확장형 팩이 있을 때)

B 모드 팩(제목에 "(확장)" 표기, ⑥ 교차 인용 포함)은 원고 대조 검증을 이미 마친 상태이므로 퇴고의 1차 근거로 사용한다:

1. **"검증 결과: 불일치" 항목 = 필수 수정 체크리스트.** 원고의 해당 위치("원고 인용 위치" 기재)를 찾아 출처 데이터 기준으로 수정한다. 불일치 항목을 남긴 채 퇴고를 종료하지 않는다
2. **⑥ 교차 인용 = Pass 1 #10(중복·모순) 점검 근거.** 다른 챕터와 겹치는 개념·수치는 재설명을 제거하고 "N장에서 다룬 [개념명]" 참조로 전환한다
3. **"원고 인용 위치" = 사례 배치 점검 근거.** 사례가 지정 위치와 다른 곳에 있으면 배치 적절성을 판단한다

### A 모드 팩 작업 순서 (기본형 팩만 있을 때)

1. 대상 챕터 원고를 읽는다
2. 해당 챕터의 참조 자료 팩을 읽는다
3. 자료 팩의 5슬롯(핵심 팩트, 인용 가능 수치, 사례·레퍼런스, 반론·주의점, 관련 키워드)을 원고와 대조한다
4. **근거 보강**: 주장만 있고 근거가 없는 문장에 수치·출처를 추가한다
5. **사례 교체·추가**: 일반적 사례를 더 구체적인 사례로 교체하거나, 빠진 사례를 추가한다
6. **균형 잡기**: 반론·주의점 슬롯의 내용을 반영해 일방적 서술을 보완한다
7. 3회 패스 편집을 실행한다

원고 대조 검증이 필요한데 A 모드 팩만 있으면, book-research B 모드 확장(기존 팩 → 확장 재생성)을 먼저 제안한다.

## 산출물·저장 규약

| 파일 | 설명 |
|------|------|
| 편집된 원고 | 3회 패스 편집이 적용된 챕터/원고 (.md 또는 .docx) |
| 편집 리포트 | Pass별 점검 결과, 주요 변경 사항, 수정 건수, 재검증 결과 요약 |

**저장·백업 규칙:**
- 저장 위치는 원고가 있던 위치(책 프로젝트 폴더)를 따른다
- **원본 파일을 직접 수정할 때는 먼저 `파일명_YYYYMMDD-HHMM.확장자`로 백업한 뒤 진행한다** (사용자가 손댔을 가능성이 있는 .docx/.md 공통)
- 별도 파일로 저장할 때는 `chapter-01-edited.docx` 형식을 쓴다(챕터 번호 2자리). 파이프라인이 자동 탐색하는 패턴이므로 임의로 바꾸지 않는다. 원고가 이 패턴을 따르지 않으면 시작 전에 1줄로 확인한다
- 편집 리포트는 대화창 제시가 기본이며, 파일 저장은 요청 시에만 한다

**편집 리포트 형식:**

```markdown
# 퇴고 리포트 — Ch{번호} {제목}

## 실행 모드: Standard / Light / Deep

## Pass 1: 구조 편집
- 점검 항목: 14개 중 {N}개 수정
- 주요 변경: [변경 내용 요약]

## Pass 2: 문장 편집
- 점검 항목: 11개 중 {N}개 수정
- 금지어 제거: {N}건
- AI 흔적 제거: {N}건
- 종결어미 수정: {N}건

## Pass 3: 교정
- 맞춤법·띄어쓰기: {N}건
- 서식 수정: {N}건
- [TODO] 처리: {N}건

## 재검증 (Evaluator)
- 결과: 통과 / 재수정 {N}회 후 통과 / 미달 보고

## 최종 글자 수: {N}자 (원본 대비 {N}%)
```

## 문체 가이드 적용 우선순위

문체 기준은 프로젝트당 하나만 둔다. 아래 순서로 찾아 **처음 발견된 것 하나만** 적용한다. 여러 개를 섞지 않는다.

| 순위 | 위치 | 비고 |
|------|------|------|
| 1 | 프로젝트 폴더 `context/writing-style-override.md` | 프로젝트 고유 오버라이드 |
| 2 | 프로젝트 폴더 `문체 기준.md` | 사용자가 만든 경우 |
| 3 | 별도 문체(보이스) 스킬 | 설치되어 있으면 호출 |
| 4 | 원고 프로젝트 폴더의 `hongstyle*.md` | 프로젝트에 사본이 있는 경우 |

**이 스킬 폴더에는 문체 파일이 들어 있지 않다.** 위 4개 위치를 순서대로 확인하고, 하나도 없으면 원고의 기존 문체를 기준으로 삼아 일관성만 점검한다. 없는 파일을 찾느라 퇴고를 멈추지 않는다. 어느 정본을 적용했는지 편집 리포트에 1줄로 명시한다.

금지어·문장 구조·분량 통제는 문체 정본과 무관하게 아래를 적용한다.
- 금지어: 혁신적인, 획기적인, 완벽한, 매우, 쉽게, 빠르게, "~할 수 있습니다 + 추상명사" 문장
- 분량: Light 105%, Standard·Deep 120% 초과 시 사유 확인

이탈 징후 3개 항목(방법이 기준보다 앞서는가 / 감정이 논리를 앞서는가 / 기준 변화 없이 "뭘 하면 되지?"만 남는가)은 문체 정본이 무엇이든 Pass 1의 #11~#13에서 점검한다.

## 다음 단계 안내 (파이프라인 후속)

퇴고 완료 후 사용자에게 후속 단계를 분기 안내한다:

- **출처 표기·참고문헌** → `book-citation` (원고 내 인용·참조를 탐지해 정식 출처 표기와 참고문헌 목록 생성. research-ChXX.md의 출처 정보가 1차 소스)
- **독자 관점 검증** → `book-feedback-reader` (타깃 독자 페르소나 시뮬레이션으로 막힘·이탈 지점 점검)
- **편집자 관점 검증** → `book-feedback-editor` (투고·출간 전 콘셉트·구조·시장성 진단)
- **원고 검증 리서치** → `book-research` B 모드 (미해소 `[TODO-FACT]`·`[TODO-EXAMPLE]`의 출처 대조)

설치되어 있지 않은 스킬은 호출하지 않는다. 대체 경로로 진행하고 그 사실을 1줄로 남긴다.

## 주의사항

- 퇴고는 "고치는 것"이지 "다시 쓰는 것"이 아니다. 작가의 목소리를 보존하면서 정비하는 것이 목표다
- Light 모드에서 분량이 원본 대비 105%를 초과하면 사유를 먼저 확인한다
- Standard/Deep 모드에서도 120%를 초과하면 사유를 확인한다
- 종결어미는 프로젝트 전체에서 통일한다. 한 챕터 안에서 `~다`체와 `~합니다`체가 혼용되면 반드시 수정한다
- `[TODO]` 마커는 book-writing-pro와 동일한 6종 체계를 사용한다: `[TODO-FACT]` 수치·사실 확인, `[TODO-IMAGE]` 이미지 추가, `[TODO-LINK]` 장 참조 확인, `[TODO-EXAMPLE]` 예시 보강, `[TODO-REVIEW]` 저자 판단, `[TODO-EXP]` 경험 삽입. 퇴고에서 해소하지 못한 `[TODO-FACT]`·`[TODO-EXAMPLE]`은 book-research B 모드로, `[TODO-EXP]`는 book-writing-pro Phase 4로 전환을 제안한다
