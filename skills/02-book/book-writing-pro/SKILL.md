# 책쓰기 전문 워크플로우 (Book Writing Pro Workflow) v1.2

7단계 구조적 집필 프로세스. 기본 책쓰기 워크플로우에 **작가 관점 선언**과 **경험·사례 주입** 단계를 추가한 전문 버전이다. 각 단계는 독립적 .docx 산출물을 생성한다.

## 전체 흐름

```
Phase 1: 기획 → Phase 2: 목차설계 → Phase 3: 챕터별 집필 → Phase 4: 경험·사례 주입 → Phase 5: 원고 통합 점검 → Phase 6: 퇴고 → Phase 7: 최종편집
```

사용자의 현재 상태를 파악해 적절한 단계부터 시작한다.
- 주제만 있음 → Phase 1부터
- **기획 인계 블록(00 기획 인계.md) 있음 → Phase 1~2를 인계 블록에서 초기화한 뒤 Phase 3부터**
- 목차/아웃라인 업로드 → Phase 2 또는 3부터
- 기존 원고 업로드 → Phase 6부터

## 파이프라인 규약

책 프로젝트 폴더에 `00 파이프라인 규약.md`가 있으면, 파일명·문체 정본·역할 경계에서 이 스킬의 기본값보다 규약 파일을 먼저 따른다. 규약 파일은 선택 사항이다. 없으면 이 문서의 기본값으로 진행한다.


## 파이프라인 입력 (기획 인계 블록·리서치 팩)

작업 시작 시 책 프로젝트 폴더에서 아래 파일을 탐색한다.

| 파일 | 출처 스킬 | 활용 |
|------|----------|------|
| `00 기획 인계.md` | book-planning | Phase 1~2 초기화 (아래 규칙) |
| `research-Ch[번호].md` | book-research | Phase 3 챕터 집필 시 "참조 자료" |

**기획 인계 블록 초기화 규칙:**
- Phase 1 기획 정보(장르·주제·독자·차별점)와 작가 관점 선언의 초기값을 인계 블록 슬롯 0(기본 정보)·1(콘셉트)·2(독자 프로필)에서 가져온다. 사용자에게는 재질문하지 않고 **확인만** 받는다
- **종결어미는 슬롯 0의 값을 그대로 쓴다.** 슬롯 0이 `[미정]`일 때만 사용자에게 묻는다
- Phase 2 목차는 인계 블록 슬롯 3(목차)·4(챕터별 개요)를 기반으로 검토·확정한다
- 경험·사례 뱅크는 인계 블록 슬롯 5(경험 소재 요청 목록)로 프리필한다
- 인계 블록과 사용자 발언이 충돌하면 사용자 발언을 우선하고, 인계 블록 갱신을 제안한다

파일이 없으면 Phase 1부터 정상 진행한다. 인계 블록이 없다고 book-planning 실행을 강제하지 않는다.

## 문체 기준

문체 기준은 프로젝트당 하나만 둔다. 아래 순서로 찾아 **처음 발견된 것 하나만** 적용한다. 여러 개를 섞지 않는다.

| 순위 | 위치 |
|------|------|
| 1 | 프로젝트 폴더 `context/writing-style-override.md` |
| 2 | 프로젝트 폴더 `문체 기준.md` |
| 3 | 별도 문체(보이스) 스킬 (설치되어 있으면 호출) |
| 4 | 이 스킬 폴더의 `hongstyle2.md` |

없는 파일을 찾느라 작업을 멈추지 않는다. 1~3순위 중 하나를 적용했으면 `hongstyle2.md`는 금지어·분량 규칙에만 쓴다. 적용한 정본이 무엇인지 챕터 산출물 보고에 1줄로 명시한다.

> **참조:** `hongstyle2.md`
> 1~3순위가 모두 없으면 챕터 작성 전 이 파일을 읽는다. 어조, 서술 시점, 문체 리듬, 어휘, 논리 전개, 핵심 규칙 5가지, 이탈 징후를 포함한다.

**이탈 징후 점검 시점:** 문체 정본이 무엇이든, 챕터 초안 완성 직후 이탈 징후 3개 항목(방법이 기준보다 앞서는가 / 감정이 논리를 앞서는가 / 기준 변화 없이 "뭘 하면 되지?"만 남는가)으로 자가 점검한다. 하나라도 해당하면 해당 문단/소제목을 재작성한다. 퇴고 Phase 6 Pass 1에서도 동일 항목을 구조 편집 체크리스트에 포함하여 재점검한다.

## Phase 1: 기획 (Planning)

기획 인계 블록(`00 기획 인계.md`)이 있으면 아래 수집 항목을 인계 블록에서 초기화하고 확인만 받는다. 없으면 사용자에게 다음 정보를 수집한다:

1. **장르·형식**: 실용서/가이드북/교재/에세이/소설 등, 예상 분량
2. **핵심 주제**: 전제(premise), 핵심 질문, 또는 해결하려는 문제
3. **독자 정의**: 누구를 위한 책인지, 독자의 현재 수준과 기대 수준
4. **차별점**: 기존 유사서 대비 이 책만의 관점·구조·접근법
5. **종결어미**: ~다체 또는 ~합니다체. 장르·형식에 따라 추천하되 사용자가 최종 결정한다. 미지정 시 ~합니다체를 기본값으로 적용한다. 선택 기준은 `writing-principles.md`의 종결어미 선택 기준 표를 참조한다

### 작가 관점 선언 (Book Perspective)

Phase 1에서 기획 정보 수집과 함께, **이 책에서 작가가 말하고 싶은 것**을 구조화한다. 이 관점 선언이 이후 전 단계의 톤·방향·판단 기준을 결정한다.

> **참조:** `book-perspective-template.md`
> 이 템플릿을 기반으로 사용자와 대화하며 관점을 구체화한다.

수집 항목:

| 항목 | 질문 | 용도 |
|------|------|------|
| 핵심 주장 | "이 책을 한 문장으로 말하면?" | 전 챕터 관통 메시지 |
| 차별 시각 | "기존 책들과 다른 나의 시각은?" | 소제목·논리 전개 방향 |
| 독자에게 남길 판단 기준 | "독자가 이 책을 읽고 스스로 판단할 수 있게 되는 것은?" | 챕터별 마무리 설계 |
| 반복 키워드·개념 | "이 책에서 자주 등장할 핵심 용어와 내 정의는?" | 용어 일관성, glossary |
| 판단 문장 비율 | "이 책의 성격에 맞는 판단:설명 비율은?" | 문체 톤 조절 |
| 쓰지 않을 것 | "이 책에서 의도적으로 배제하는 접근·표현·범위는?" | anti-patterns |
| 경험 vs 근거 구분 | "내 경험에서 온 주장과 외부 근거의 비중은?" | 서술 톤 구분 |

**처리 규칙:**
- 7개 항목을 한꺼번에 묻지 않는다. 대화 흐름에서 자연스럽게 수집한다.
- 핵심 주장, 차별 시각, 쓰지 않을 것 — 이 3개가 최소 필수 항목이다. 나머지는 집필 과정에서 보완 가능하다.
- 기획 인계 블록이 있으면 핵심 주장·차별 시각의 초안을 인계 블록 슬롯 1(콘셉트)·6(차별점)에서 가져와 확인받는다.
- 수집된 관점은 `book-perspective-{프로젝트명}.md`로 저장하여 이후 단계에서 참조한다.

### 산출물: `01-book-plan.docx`

다음 항목을 포함:
- **책 개요**: 가제, 장르, 독자층, 예상 분량, 차별점, **종결어미(~다체 또는 ~합니다체)**
- **핵심 전제/논지**: 1~2문단 요약
- **작가 관점 선언**: Phase 1에서 수집한 관점 구조화 (이후 전 단계에서 참조)
- **독자 프로필**: Phase 1에서 수집한 독자 정의를 구체화 (이후 전 단계에서 참조)
- **구조 방향**: 전체 흐름 개요 (이해 → 설계 → 실행 → 확장 등)
- **캐릭터 프로필** (소설): 이름, 역할, 아크, 핵심 특성
- **리서치 노트** (논픽션): 조사 필요 주제, 핵심 자료 목록
- **일정**: 집필 마일스톤 (사용자에게 마감일 확인)

### 산출물: `book-perspective-{프로젝트명}.md`

작가 관점 선언 파일. 다음 항목을 포함:
- 핵심 주장 (한 문장)
- 차별 시각
- 독자에게 남길 판단 기준
- 반복 키워드·개념 정의 (glossary)
- 판단 문장 비율 기준
- 쓰지 않을 것 (anti-patterns)
- 경험 vs 근거 구분 기준

구조 템플릿이 필요하면 `book-perspective-template.md`를 참고한다.

## Phase 2: 목차설계 (Structure Design)

Phase 1의 기획 문서와 **작가 관점 선언**을 기반으로 상세 목차를 설계한다. 기획 인계 블록이 있으면 슬롯 3(목차)·4(챕터별 개요)를 초안으로 삼아 검토·확정한다.

### 목차 설계 원칙

- 장(Chapter) 구성은 **이해 → 설계 → 실행 → 확장** 흐름을 기본 골격으로 삼되, 장르에 따라 조정
- 각 장은 2~4개 소제목으로 구성
- **소제목은 기능명이 아닌 행동·판단 중심 문장으로 작성**
  - ❌ "레이어 기능" → ✅ "레이어로 구조를 분리하는 기준"
  - ❌ "색상 설정" → ✅ "색상 선택이 결과에 미치는 영향을 판단하는 법"
- 각 장 말미에 반드시 **실무 정리 블록** 포함 계획:
  - 적용 체크리스트
  - 자주 발생하는 실수
  - 구조 예시 (프롬프트, 워크플로우 등)
- **작가 관점 선언의 핵심 주장이 목차 전체를 관통하는지 확인한다.** 핵심 주장과 무관한 챕터가 있으면 삭제하거나 연결 논리를 보강한다.

### 경험·사례 뱅크 초기 구성

목차 설계와 동시에, 챕터별로 삽입 가능한 경험·사례를 미리 수집한다.

> **참조:** `experience-bank-template.md`
> 이 템플릿을 기반으로 챕터별 경험 메모를 정리한다.

기획 인계 블록이 있으면 슬롯 5(경험 소재 요청 목록)의 챕터별 `[소재 필요]` 항목을 경험 뱅크의 초기 골격으로 옮긴 뒤, 부족한 부분만 질문한다.

사용자에게 각 챕터에 대해 다음을 질문한다 (강제하지 않고, 떠오르는 것만 수집):
- "이 주제와 관련된 직접 경험이 있는가?"
- "수강생이나 클라이언트에게서 본 사례가 있는가?"
- "이 주제에서 실패한 경험이 있는가?"
- "생각이 바뀐 계기가 있는가?"

수집된 내용은 `experience-bank-{프로젝트명}.md`에 정리한다. Phase 3에서 초안 작성 시 참조하고, Phase 4에서 추가 삽입한다.

### 프로젝트별 확정 목차 참조

프로젝트별 확정 목차가 별도 파일(예: `references/project-toc.md`)로 존재하면 이를 참조한다. 챕터 작성 시 전체 구조 안에서의 위치, 앞뒤 챕터와의 연결, 파트별 톤을 반드시 확인한다.

### 산출물: `02-table-of-contents.docx`

다음 항목을 포함:
- **전체 목차**: Part → Chapter → 소제목 계층 구조
- **챕터별 시놉시스**: 각 챕터 2~3문장 요약 (목적, 핵심 내용, 독자가 얻는 것)
- **챕터별 예상 분량**: 글자 수 범위
- **챕터 간 연결 논리**: 앞 챕터에서 다음 챕터로 이어지는 흐름 설명

### 산출물: `experience-bank-{프로젝트명}.md`

챕터별 경험·사례 뱅크 초안. Phase 3~4에서 지속 업데이트.

## Phase 3: 챕터별 집필 (Chapter Drafting)

Phase 2의 목차를 청사진으로 사용한다. 사용자가 기존 아웃라인을 업로드한 경우 그것을 기반으로 한다.

### 집필 전 참조 파일

챕터 작성 전 반드시 다음 파일을 확인한다 (우선순위 순):
1. **저자 문체 예시** (`hongstyle2.md`, 내 문체로 교체 가능) — 어조, 리듬, 핵심 규칙, 이탈 징후
2. **작가 관점 선언** (`book-perspective-{프로젝트명}.md`) — 핵심 주장, 차별 시각, 쓰지 않을 것
3. **경험·사례 뱅크** (`experience-bank-{프로젝트명}.md`) — 해당 챕터에 배정된 사례
4. **챕터 참조 자료 팩** (`research-Ch[번호].md` — book-research 산출) — ① 핵심 팩트·② 인용 가능 수치·③ 사례를 "참조 자료"로 사용. 프로젝트 폴더에서 자동 탐색하고, 없으면 생략하거나 book-research 실행을 제안한다
5. **챕터 템플릿** (프로젝트별 별도 파일이 있으면 참조)

그 외 파일(glossary, anti-patterns, writing-principles)은 필요 시에만 참조한다.

### 컨텍스트 리셋 규칙

**매 챕터 진입 시 아래 3개 항목을 반드시 재확인한다.** 같은 대화에서 이전 챕터를 이미 작성했더라도, 새 챕터 시작 전에 다시 확인한다. 긴 대화에서 앞쪽 규칙이 희석되는 것을 방지하는 장치다.

1. **종결어미** — Phase 1에서 결정된 종결어미(~다체 또는 ~합니다체) 재확인
2. **작가 관점** — 이 챕터에서 적용할 핵심 주장·차별 시각 재확인
3. **독자 프로필** — 독자 수준과 이 챕터에서의 난이도 위치 재확인

3챕터 연속 작성 후에는 금지어 규칙(①~⑥)도 재확인한다.

### 챕터 출력 슬롯 템플릿 (초안은 반드시 이 구조를 따른다)

챕터 초안은 아래 슬롯을 순서대로 채운다. 슬롯을 건너뛰거나 순서를 바꾸지 않는다.

```
[도입] ← 챕터 오프닝. 챕터 기능에 맞는 오프닝 유형으로 설계 (후크 → 다리 → 약속, 3~6문장)
[소제목 1] ← 개념 또는 판단 기준 제시
  [기준] ← 핵심 판단 기준 1문장
  [근거/사례] ← 기준을 뒷받침하는 설명·경험
[소제목 2~N] ← 동일 구조 반복
[실무 정리 블록] ← 체크리스트 / 자주 하는 실수 / 구조 예시
[연결] ← 다음 장으로의 전환 문장
```

소제목 안의 내용은 자유롭게 작성하되, **[기준] → [근거/사례] 순서는 역전하지 않는다.** 근거나 방법부터 시작하면 "그래서 뭘 하면 되지?"만 남는 글이 된다.

### 챕터 오프닝 설계 ([도입] 슬롯)

> **참조:** `chapter-opening.md`
> [도입] 슬롯을 채우기 직전에 이 파일을 읽는다. 오프닝 유형 5종, 챕터 기능별 매칭, 생성-평가 절차, 평가 기준, 금지 패턴을 포함한다.

[도입]은 단일 패턴("왜 이 주제가 필요한가")으로 고정하지 않는다. 챕터 기능(개념 도입 / 방법론 / 근거 / 관점 전환)에 따라 오프닝 유형을 매칭하고, 후보를 3개 생성한 뒤 평가 기준으로 1개를 선별한다. 절차 상세는 `chapter-opening.md`를 따른다. 작가 관점 선언과 독자 프로필을 입력으로 반영하여, 챕터마다 다른 오프닝이 나오게 한다.

### 집필 규칙

- **챕터 단위로 작성**, 각각 별도 `.docx` 파일로 저장
- 각 챕터 시작 시 내부 메모 포함: 챕터 목표, 핵심 포인트, 목표 분량, **이 챕터에서 적용할 작가 관점**
- 일관된 문체, 시제, 서술 시점 유지
- 확인/보완 필요 구간은 유형별 `[TODO-유형: ...]` 마커 삽입 (공통 집필 원칙의 TODO 마커 유형 분류 참조)
- 경험·사례 뱅크에 해당 챕터 사례가 있으면 초안에 반영한다. 없으면 `[TODO-EXP: ...]` 마커를 삽입한다
- 실용서 기본 분량: 챕터당 3,000~6,000자 (사용자 지정 가능)

### 챕터 집필 프로세스

1. 목차에서 해당 챕터 시놉시스 확인
2. **작가 관점 선언에서 이 챕터에 해당하는 관점 확인**
3. **경험·사례 뱅크에서 이 챕터에 배정된 사례 확인**
4. **챕터 참조 자료 팩(`research-Ch[번호].md`)이 있으면 필요한 슬롯(①②③④)을 선별 확인**
5. **첫 문장: 챕터 기능에 맞는 오프닝 유형으로 설계** (`chapter-opening.md` 참조, 기능 소개·메타 선언 시작 금지)
6. 개념 → 판단 기준 → 실제 적용 방식 순서로 본문 전개
7. 경험 뱅크의 사례를 본문 논리 흐름에 자연스럽게 배치
8. 문단은 2~4문장 이내 유지 (최대 5문장)
9. 챕터 끝: 다음 장으로의 연결 문장 + 실무 정리 블록
10. 유형별 `[TODO-유형: ...]` 마커 삽입 (리서치/검토/경험 필요 부분)
11. **초안 자가 점검 (출력 전 반드시 실행)**: 초안 완성 직후 아래 전체 항목 확인.

    **이탈 징후 점검:**
    - [ ] 방법·팁·요령이 기준 설명 없이 먼저 등장하는가?
    - [ ] 감정적 공감이나 동기 부여 문장이 논리 설명보다 앞서는가?
    - [ ] 글을 읽고 난 뒤 기준 변화 없이 "그래서 뭘 하면 되지?"만 남는가?

    **금지어·문체 점검:**
    - [ ] "혁신적인", "획기적인", "완벽한" 등 과장형 형용사 포함 여부
    - [ ] "~할 수 있습니다" 추측 표현 포함 여부
    - [ ] "매우", "쉽게", "빠르게" 등 모호한 부사 포함 여부
    - [ ] 추상 명사 중심 문장 포함 여부

    **슬롯 구조 점검:**
    - [ ] [기준] → [근거/사례] 순서가 지켜졌는가?
    - [ ] [실무 정리 블록]이 누락되지 않았는가?

    **오프닝 점검 (`chapter-opening.md` 기준):**
    - [ ] [도입] 첫 문장이 구체(장면·사실·질문·대조)로 시작하는가?
    - [ ] "이번 장에서는 ~를 다룬다" 식 메타 선언이 없는가?
    - [ ] 후크 → 챕터 주제 연결(다리)이 있는가?

    → 하나라도 해당하면 해당 문단/소제목을 재작성한다. **수정 후 재점검은 최대 2회.** 2회 후에도 미달 항목이 남으면 미달 항목·위치·사유를 사용자에게 보고하고 판단을 요청한다. 점검 결과는 초안 제시 시 1줄로 함께 표기한다
12. `chapter-XX-draft.docx`로 저장

### Phase 3 → Phase 4 전환 규칙

전 챕터를 모두 완성한 뒤 Phase 4로 넘어가는 것이 기본이지만, **파트(Part) 단위 순환도 허용한다.**

**전환 모드:**

| 모드 | 흐름 | 적합한 경우 |
|------|------|------------|
| 일괄 전환 | 전 챕터 Phase 3 완료 → 전 챕터 Phase 4 | 챕터 수 10개 이하, 경험 뱅크가 미리 정리된 경우 |
| 파트 단위 순환 | Part A Phase 3 → Part A Phase 4 → Part B Phase 3 → Part B Phase 4 → ... | 챕터 수 12개 이상, 앞 파트 경험 삽입 결과가 뒤 파트 집필에 영향을 줄 때 |

- 사용자가 모드를 지정하지 않으면 **일괄 전환**을 기본값으로 한다.
- 파트 단위 순환 시, Phase 5(통합점검)는 **모든 파트의 Phase 4가 끝난 후** 1회만 실행한다.
- 어떤 모드든, Phase 4 진입 전 해당 챕터의 초안이 이탈 징후 자가 점검을 통과한 상태여야 한다.

## Phase 4: 경험·사례 주입 (Experience Injection)

Phase 3의 초안이 완성된 후, 각 챕터에 작가의 경험·사례를 삽입하는 단계. **논리 골격 위에 경험을 얹어, 경험이 "증거"로 작동하게 만드는 것**이 이 단계의 목적이다.

### 왜 Phase 3 이후인가

Phase 3의 초안은 논리 골격이다. 개념 → 판단 기준 → 적용 방식이 잡혀 있는 상태. 이 골격 위에 경험을 얹어야 경험이 논증의 도구로 기능한다. 골격 없이 경험부터 쓰면 수필이 되고, 경험 없이 퇴고에 들어가면 "맞는 말인데 와닿지 않는 글"이 된다.

### 작업 흐름

```
초안 읽기 → [TODO-EXP] 마커 확인 → 작가 경험 입력 → 본문 녹여쓰기 → 경험 로그 기록
```

### 경험 주입 입력 템플릿

경험 주입 입력 템플릿은 `prompt-templates.md` 2절을 쓴다.

### "Claude 판단에 맡김" 위치 선정 기준

`book-writing-rules.md`의 같은 이름 절을 따른다.

### 처리 규칙

1. **경험은 별도 박스나 칼럼으로 분리하지 않는다.** 본문 논리 흐름 안에 녹인다
2. 경험 문단의 톤: 해당 유형의 서술 톤을 따르되, 반드시 판단 기준으로 귀결한다
3. 삽입 후 해당 소제목의 분량이 원본 대비 130%를 초과하면 작가에게 확인한다
4. 하나의 챕터에 경험 유형이 편중되지 않도록 유형 분포를 리포트한다
5. `[TODO-EXP]` 마커가 남아 있으면 작가에게 알린다 — 경험 없이 넘어갈지, 추가할지 확인
6. 경험 뱅크(`experience-bank-{프로젝트명}.md`)에 있으나 Phase 3 초안에 반영되지 않은 사례도 이 단계에서 삽입한다
7. 삽입된 경험은 `hongstyle2.md` 핵심 규칙 3번("사례는 결론을 증명하기 위한 도구로만 사용한다")을 따른다

### 경험 삽입 품질 체크

각 삽입된 경험에 대해 다음을 확인한다:

| # | 점검 항목 | 상태 |
|---|----------|------|
| 1 | 경험이 해당 소제목의 판단 기준을 뒷받침하는가 | ☐ |
| 2 | 경험이 본문 논리 흐름에 자연스럽게 연결되는가 (별도 블록처럼 보이지 않는가) | ☐ |
| 3 | 경험의 서술 톤이 유형에 맞는가 (1인칭/3인칭, 구체성 수준) | ☐ |
| 4 | 경험이 감정 표현이나 동기 부여로 빠지지 않고 판단 기준으로 귀결되는가 | ☐ |
| 5 | 동일 경험이 다른 챕터에서 중복 사용되지 않는가 | ☐ |

## Phase 6: 퇴고 (Revision & Editing)

### 역할 전환 선언 (퇴고 진입 조건)

이 단계에서는 집필자의 시점을 내려놓는다. 편집자로서, 집필 의도를 참고하지 않고 **독자 시점에서만 판단**한다. "왜 이렇게 썼는가"가 아니라 "독자가 읽었을 때 작동하는가"를 기준으로 점검한다. 이 선언 없이 체크리스트를 돌리면, 구조적 문제보다 표현만 다듬는 쪽으로 흐른다.

**3회 패스 퇴고의 정본은 `book-editing` 스킬이다.** 이 Phase는 퇴고 절차를 다시 정의하지 않고 book-editing을 호출한다. 같은 절차를 두 문서에 두면 한쪽만 갱신되어 결과가 갈린다.

**호출 규칙:**
1. `book-editing`이 설치되어 있으면 Skill 도구로 호출한다. 입력은 Phase 5 통합 원고, 모드는 Standard를 기본으로 하고 B 모드 리서치 팩이 있으면 Deep으로 올린다
2. 설치되어 있지 않으면 이 스킬 폴더의 `editing-checklist.md`로 대체 실행한다. Pass 1(구조 14항목), Pass 2(문장 11항목 + 금지어 6항목), Pass 3(교정 9항목)
3. 어느 경로로 실행했는지 산출물 보고에 1줄로 명시한다

챕터 단위 수시 퇴고도 book-editing 단독 실행이 기본이다. 이 Phase는 전체 원고 통합 후 최종 퇴고를 담당한다.

| `06-manuscript-edited.docx` | 퇴고 완료 원고 |
| `06-editing-report.docx` | 3회 패스 체크리스트 결과 + 주요 변경 사항 기록 |

## Phase 7: 최종편집 (Final Polish)

퇴고 완료 원고를 출판/배포 수준으로 마무리한다.

### 최종편집 항목

1. **서문(프롤로그)**: 책의 목적, 독자에게 하는 약속, 이 책의 활용법
2. **에필로그/맺음말**: 전체 여정 요약, 독자의 다음 단계 제시
3. **각 챕터 도입부 훅(hook) 점검**: `chapter-opening.md` 평가 기준(구체성·연결성·메타 선언 없음·관점 반영·분량)으로 전 챕터 도입을 최종 점검. 동일 오프닝 유형이 3챕터 연속 반복되면 교체 검토
4. **부록 정리**: 참고 자료, 용어 사전, 추가 리소스
5. **표지·판권 페이지**: 가제 확정, 저자 정보
6. **전체 흐름 최종 검수**: 처음부터 끝까지 읽으며 독자 경험 점검
7. **작가 관점 최종 확인**: 핵심 주장이 서문~에필로그까지 일관되게 관통하는지 점검

### 산출물: `07-manuscript-final.docx`

최종 완성본. 다음을 포함:
- 표지 페이지
- 목차 (자동 생성)
- 서문
- 전체 챕터
- 에필로그
- 부록 (해당 시)
- 판권 페이지

## 다음 단계 안내 (파이프라인 후속)

집필·퇴고가 끝나면 사용자에게 후속 단계를 분기 안내한다:

- **챕터 단독 퇴고** → `book-editing` (3회 패스 퇴고의 정본)
- **원고 검증 리서치** → `book-research` B 모드 (원고 수치·사례를 출처와 대조, `[TODO-FACT]` 해소)
- **출처 표기·참고문헌** → `book-citation` (research-ChXX.md의 출처 정보가 1차 소스가 되어 재검색을 줄인다)
- **독자 관점 검증** → `book-feedback-reader` (타깃 독자 페르소나 시뮬레이션)
- **편집자 관점 검증** → `book-feedback-editor` (투고·출간 전 콘셉트·구조 진단)

설치되어 있지 않은 스킬은 호출하지 않는다. 대체 경로로 진행하고 그 사실을 1줄로 남긴다.

## 산출물·폴더 구조·장르 가이드

> **참조:** `project-setup-guide.md`
> 산출물 총괄(12개 파일), 프로젝트별 폴더 구조, glossary/anti-patterns 분리 기준, 파일 참조 우선순위(7단계), 장르별 분량·경험 비율 가이드를 포함한다.

**저장·형식 규약:**
- 챕터 파일의 `XX`는 2자리 챕터 번호다(`chapter-01-draft.docx`, `chapter-10-enriched.docx`). 파이프라인이 자동 탐색하는 패턴이므로 임의로 바꾸지 않는다
- 모든 산출물은 `.docx` 형식을 기본으로 한다. 문서 생성 전 반드시 docx 스킬(SKILL.md)을 읽고 따른다
- 저장 위치는 책 프로젝트 폴더를 기본으로 한다. 하위 폴더는 사용자가 요청할 때만 만든다
- 사용자가 옵시디언 등 마크다운 편집기에서 직접 다루는 원고는 요청 시 `.md`로 병행 생성한다. 이때 .docx와 .md의 기준본이 무엇인지 1줄로 명시한다
